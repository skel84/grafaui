Prometheus variable investigation — 2026-10-03

Cause and correction
--------------------
Kubernetes Views dashboards query label_values(kube_node_info,cluster).
The live cluster has 6 kube_node_info series, all without a cluster label.
Prometheus permits cluster="" to match those unlabeled series. Grafaui was
incorrectly treating a successful empty variable result as a fatal error.

Successful empty variable results now resolve to an empty selection with a
visible warning. Saved choices are discarded when absent from the live result.
The warning does not block dependent variables or panel requests. HTTP/API
failures and unsupported queries remain errors; fake data is never substituted.
Empty variable controls display Empty; controls are disabled while resolving.

Grafana-compatible default multi/All interpolation no longer groups a single
value, and it escapes RE2 metacharacters without escaping hyphens. A single
job selection now produces job="node-exporter", instead of a parenthesized
regex string in an exact equality matcher. Multiple selections remain regex
alternations; dashboards must use regex matchers to support multiple/All values.

label_values requests now use /api/v1/label/<label>/values with match[], start
and end. Broad container selectors previously fetched all series and hit the
64 MiB response limit. The compact endpoint returns distinct values directly.

returns no samples. These panels correctly show No data.

Pods: the default All selection has custom value .*. Several stat targets use
pod="$pod" (exact equality), which becomes pod=".*" and matches no real pod.
Select an individual pod for those targets, or adjust the dashboard to use =~.
Other empty results depend on each fixture's metric/label selectors and events.
Grafaui preserves these expressions instead of rewriting their meaning.

Environment
-----------
Only read-only API queries and local port-forwards were used. No cluster
resources were changed. The pre-existing user forward on 19090 stopped
responding during the broader audit; a fresh forward to the same service on
19092 worked. The pre-existing forward was left untouched. Only the forward
and native app processes started for this investigation were stopped.

Reproduce with a fresh forward (first terminal):
kubectl --kubeconfig ~/code/home-ops/kubeconfig -n observability port-forward --address 127.0.0.1 svc/kube-prometheus-stack-prometheus 19092:9090

Native app (second terminal, after cargo build --release):
./target/release/grafaui fixtures/real/15757.json --prometheus-url http://127.0.0.1:19092 --scrape-interval 30

Variable-only diagnostic:
cargo run --release --locked -p grafaui-prometheus --example check -- http://127.0.0.1:19092 fixtures/real/15757.json now-1h 30 --variables-only
